# 스폰 시스템 설계 문서

탑다운 뷰 기반의 군집 스폰/AI 시스템. 헬다이버즈2의 순찰·증원과 스타크래프트2 협동전의
웨이브·목표 구조에서 영감을 받음. 몬스터는 프리미티브 오브젝트 기준.

> 이 문서는 코드 이전에 합의한 설계의 단일 진실(single source of truth). 구현 중 결정이
> 흔들리면 이 문서를 기준으로 판단하고, 변경 시 이 문서를 먼저 고친다.

---

## 1. 핵심 설계 결정 (locked)

| 축 | 결정 |
|---|---|
| 스폰 진행 | 하이브리드 — 연속 디렉터(예산·긴장도) + 스크립트 이벤트(목표/정시 스파이크) |
| 인지 모델 | 순찰 → 발각 → 증원 |
| 군집 이동 | 가상 앵커형 (군집이 리더를 소유, navmesh 길찾기는 군집당 1개) |
| 산출물 | 둘 다 — 에디터 제너레이터 툴 + 런타임 스포너 |
| 맵 | 평면 Plane + 큐브 벽 (높이 0, 벽은 navmesh 베이크 제외 = 도달 불가) |
| 긴장도 신호 | 경과시간 + 남은 목표수 |
| 발각 판정 | 시야 = 발각 채널, 소음 = 시야를 돌리는 트리거, 거리 = 시야 게이트 |
| 상태 소유 | 군집(Pack) 단위 공유 — 한 멤버라도 발각하면 전원 교전 |

## 2. 데이터 모델 (ScriptableObject)

- `MonsterDef` — 프리미티브 프리팹 + 스탯 + 태그(근접/원거리/엘리트/스웜)
- `SpawnEntry` — { monster, weight, cost, groupSize(min~max), minDifficulty, tags }
- `SpawnTable` — `SpawnEntry[]` + 선택 모드(WeightedRandom / BudgetFill / Sequential)
- `DirectorProfile` — 긴장도 가중치, 예산 회복률, 최대/최소 스폰 간격, 동시 개체 상한
- `EncounterScript` — 목표 달성/정시 트리거 시 발동하는 스크립트 스폰

`cost` + 예산이 난이도 스케일링의 핵심: 초반 적은 예산 → 싸구려 스웜, 후반 많은 예산 → 엘리트 구매.

> 실제 몬스터 종류(근접/원거리/증원 로스터 + 잠정 스탯)는 [Monsters.md](Monsters.md) 참조. 로스터가
> 요구하는 장갑/데미지 타입·특수능력(Leap/Burrow/Summon)·공격 정의는 §13 스키마 확장 대상(검토 중).

## 3. 런타임 시스템

- `SpawnDirector` — 긴장도·예산을 굴려 "언제·얼마나"를 결정하고 군집 스폰을 요청
- `SpawnPointProvider` — "어디"를 결정. 전략 2개:
  - `Nest` — 고정 둥지에서 스폰 (평상시)
  - `PlayerRing` — 플레이어 주변 링, 화면 밖에서 스폰 (목표 전부 처리 후 엔드게임)
- `PackSpawner` + 오브젝트 풀 — Instantiate/Destroy 금지, 재사용
- `MonsterPack` — 가상 앵커 + 멤버 리스트 + 상태머신 + 공용 칠판(blackboard)
- `Monster` — 멤버 1마리. 앵커 추종 boids(응집/분리) + 자기 시야 감지 + 전투
- `PlayerController` — 클릭 이동(navmesh, XZ 고정, 높이 고정)

## 4. 군집(Pack) — 가상 앵커 모델

- 군집은 1급 객체. 내부에 **보이지 않는 앵커**(빈 GameObject + NavMeshAgent 1개)를 가짐.
- 길찾기는 **앵커만** 수행 → navmesh 경로가 "멤버당 1개"가 아니라 "군집당 1개"로 줄어 성능 확보.
- 멤버는 앵커로 모이기(응집) + 서로 밀어내기(분리)만 하는 boids 추종자.
- 리더십은 특정 몹의 속성이 아니라 군집의 속성. 멤버가 죽으면 리스트에서 빠질 뿐, 경로/상태 영향 없음.
- 시각적 "선두"가 필요하면 앵커 기준 최전방 멤버를 겉보기로 칠하되, 길찾기 책임은 없음.

## 5. 인지 / 상태머신

발각은 스칼라 블렌딩이 아니라 **이벤트 기반 인과 사슬**:

- **시야** = 유일한 발각 채널. (시야각 안 + 사거리 안 + LoS 차단 없음) → 발각.
- **소음** = 발각이 아니라 시야를 돌리는 트리거. 플레이어 고속 이동/공격 시 반경 R 소음 이벤트 발생 →
  그 안의 군집은 소음원 쪽으로 시야를 향하고 조사. 결과적으로 플레이어가 콘에 들어오면 발각.
- **거리** = 시야의 게이트. 시야 안이어도 너무 멀면 미발각, 가까우면 확정. 시야 밖이면 거리는 무의미.
- 천천히 조용히 움직이면 순찰을 흘려보낼 수 있는 스텔스 여지 → 헬다이버즈 감각.

상태는 **군집 단위 공유**: 멤버는 각자 자기 콘으로 감지(분산 센서), 한 놈이라도 발각하면
공용 칠판의 `knownPlayerPosition`에 기록 → 전원 교전 전환. 전원이 시선을 잃고 T초 경과 시 위치가
낡아 경계(마지막 위치 수색) → 순찰 복귀.

상태 전이:

| from | to | 이벤트 |
|---|---|---|
| 순찰 | 경계 | 소음 감지 |
| 순찰 | 교전 | 직접 시야 (근거리) — 콘에 바로 들어옴 |
| 경계 | 교전 | 시야로 확인 |
| 경계 | 순찰 | 조사 실패 (타임아웃) |
| 교전 | 경계 | 시야 상실 (마지막 위치 수색) |

상태별 행동:
- **순찰** — 앵커가 스폰 당시 플레이어 위치 방향으로 전진. 플레이어를 모름.
- **경계** — 마지막 자극 위치로 이동해 조사. 못 찾으면 순찰 복귀.
- **교전** — 추격 + breach 증원 호출(둥지 추가 군집 또는 근처 가장자리 합류).

## 6. 긴장도 / 스폰 페이싱

0~1 긴장도 하나로 합쳐 스폰 간격을 조절:

```
intensity     = w_time · (경과시간 / 최대시간) + w_obj · (1 − 남은목표 / 전체목표)
spawnInterval = lerp(최대간격, 최소간격, intensity)   // 최소간격으로 clamp(무한 스폰 방지)
```

- 목표를 깰수록(남은 목표 ↓) 긴장도 ↑ → 스폰 간격 ↓. 진행 = 압박 증가 (의도된 리스크-리워드).
- 목표가 0이 되면 긴장도가 최대 쪽으로 붙으며 엔드게임으로 자연 전환.
- 엔드게임에서는 `SpawnPointProvider`가 `Nest` → `PlayerRing`으로 전환.

## 7. 맵 / 스폰 지점

- 평면 Plane(높이 0) + 큐브 벽. NavMeshSurface로 베이크 (벽은 경사 한계로 자동 제외).
- 목표(objective): navmesh 유효 지점에서 랜덤 샘플 + 서로 최소 간격 유지해 N개 배치.
- "안 보이게 스폰" 판정 = 카메라 절두체(화면 사각형) 밖. 후보점 선택 알고리즘:
  1. 플레이어 기준 반경 R 링 위 후보 N개 샘플
  2. 필터: (a) navmesh 유효 (b) 화면 밖 (c) 가능하면 벽 뒤
  3. 통과점에서 스폰, 전부 실패 시 R 키워 재시도

## 10. 개발 워크플로우 (TDD)

이 프로젝트는 **테스트 주도**로 진행한다. 스크린샷 기반 육안 검증을 최소화하고, 동작을
자동화된 테스트로 고정해 회귀를 막는 것이 목적이다.

**모든 작업은 다음 순서를 따른다** (불필요할 만큼 사소하면 생략 가능):

```
계획 → 테스트 작성 → 구현 → 검증(테스트 실행) → 최종 테스트(전체 그린 확인)
```

핵심 원칙 — **테스트 가능한 이음새(seam) 분리**:
- NavMesh / Input / MonoBehaviour 에 의존하지 않는 **순수 로직**(기하·수치 계산)을 정적 클래스로
  빼내고, MonoBehaviour 는 거기에 위임만 한다. 예: `MovementResolver`(클릭→목적지 기하),
  `BoidsSteering`(응집·분리 계산).
- 순수 로직 → **EditMode** 단위 테스트(빠름, 씬/플레이 불필요).
- NavMesh 길찾기·에이전트 등 씬이 필요한 통합 동작 → **PlayMode** 테스트(런타임 navmesh 베이크).

### 어셈블리 / 테스트 구조

| 어셈블리 | 경로 | 용도 |
|---|---|---|
| `SpawnSystem` | `Assets/Scripts/` | 런타임 코드 (asmdef 이어야 테스트가 참조 가능) |
| `SpawnSystem.Editor` | `Assets/Scripts/Editor/` | 에디터 전용 (Cinemachine/UnityEditor 격리) |
| `SpawnSystem.Tests.EditMode` | `Assets/Tests/EditMode/` | 순수 로직 단위 테스트 |
| `SpawnSystem.Tests.PlayMode` | `Assets/Tests/PlayMode/` | navmesh/에이전트 통합 테스트 |

- 패키지 어셈블리 이름: `Unity.AI.Navigation`, `Unity.InputSystem`, `Unity.Cinemachine`.
- 커스텀 테스트 도구: `NavTestEnvironment` — 바닥+벽을 절차 생성하고 런타임 NavMesh 를 베이크해
  통합 테스트 환경을 코드로 세팅(스샷 불필요).

### 테스트 실행

- 에디터: `Window > General > Test Runner` → EditMode/PlayMode 탭 → Run All.
- 자동화(MCP): `run_tests`(mode, assembly_names) → `get_test_job` 로 폴링.

## 11. 적 종류 · 물리 · 이동 방식 (요청 반영)

> **워크플로우**: 앞으로 모든 기능 추가 요청은 이 문서에 기록한다. 기획이 서로 충돌하거나
> 모호한 부분이 있으면 구현 전에 사용자에게 확인한다(추측으로 진행하지 않는다).

### 11.1 적 종류 — 크기·이동속도 차등 (요청됨)

`MonsterDef`(2장)별로 크기(에이전트 반경/스케일)와 이동속도를 다르게 둔다. **잠정** 시작 세트(수치 확정 전):

| 타입 | 태그 | 반경/스케일 | 이동속도 | 성격 |
|---|---|---|---|---|
| 스웜링 | 스웜 | 작음 (~0.3) | 빠름 (~6) | 싸고 다수, 물량 |
| 러너 | 근접 | 보통 (~0.5) | 매우 빠름 (~8) | 측면 기습 |
| 표준 | 근접 | 보통 (~0.5) | 보통 (~4) | 기본 근접 |
| 브루트 | 엘리트 | 큼 (~1.2) | 느림 (~2.5) | 탱커 / 돌파 |

### 11.2 물리적 충돌 (요청됨)

- 멤버가 **벽을 통과하면 안 된다** (현재 transform 적분 방식이라 벽 파고듦 — 수정 필요).
- 멤버끼리 **물리적 존재감**이 필요 (서로 겹쳐서 한 점에 포개지면 안 됨).

### 11.3 이동 방식 — 결정됨

목표 규모/기능(아래 가정)을 감안해 **LOD 기반 계층형 이동**으로 확정.

**가정(사용자 제시):** 동시 최대 ~300마리(한 화면에 다 보이진 않음), 멤버마다 애니메이션·공격·
랙돌 사망·부위 파괴·카오스 디스트럭션·파티클·투사체. → 멤버 1마리당 비용이 큼 → **화면 밖은 싸게,
화면 안은 정밀하게**(LOD)가 필수. 그리고 적의 이동은 **플레이어를 포위(encircle)** 해야 함
(최단거리 직선 추격은 금지 — 조잡함).

**계층 구조:**

1. **Pack Brain (저빈도, 예산제)** — 길찾기 예산은 여기만. 앵커(NavMeshAgent)가 플레이어 근처
   접근점으로 길찾기(군집당 1경로, 4장 유지). 군집의 *의도*(어디를 포위할지)를 결정.
2. **Encircle 슬롯 (순수 로직, 테스트)** — `EncircleFormation` 이 앵커(→수렴 시 플레이어) 주위 링에
   N개 슬롯을 만들고 멤버를 각도 순으로 배정. 멤버의 목표 = 자기 슬롯(앵커 점이 아님) → 포위 대형.
3. **Member Mover (추상화, LOD 교체)** — `IMemberMover`:
   - `AgentMover`(고정밀): 멤버 NavMeshAgent를 `agent.Move(steering·dt)`로 구동. **길찾기 호출 안 함**
     → navmesh가 벽 통과 차단 + 에이전트 회피(RVO)로 멤버 간 물리적 밀어냄. 화면 안/근거리.
   - `TransformMover`(저정밀): transform 적분 + (선택)navmesh 클램프. 회피·애니 없음. 화면 밖/원거리.
   - 조향 속도는 `BoidsSteering`(슬롯으로 응집 + 분리)으로 계산 → 어느 mover든 동일.
4. **LOD 컨트롤러 (군집별)** — 가시성/거리로 정밀도 선택. 완전 화면 밖+원거리 = 저정밀(걸어옴, 회피·
   애니·파티클 생략, 틱 감속). 화면 안/근거리 = 고정밀(AgentMover, 회피, 애니, 정밀 포위, 랙돌/부위파괴).

**물리 강도:** 소프트 회피(NavMeshAgent RVO) 채택. 하드 리지드바디 충돌은 다수 유닛에서 불안정해 미채택.

**4장 보정:** "멤버는 순수 boids 추종자" → "`agent.Move`로 **navmesh에 구속되는** boids 추종자(고정밀
LOD), 또는 저정밀 LOD에선 transform 추종." 길찾기는 여전히 앵커만(Move ≠ 길찾기) → 성능 의도 유지.

### 11.4 크기별 NavMesh 타입 — 결정됨

적 크기 차등은 **크기별 navmesh 타입(에이전트 타입)을 따로 베이크**해서 처리(사용자 결정). 각
`MonsterDef`는 자기 크기 클래스의 NavMesh agent type을 참조. `MapGenerator`는 사용되는 크기 클래스마다
`NavMeshSurface`를 하나씩 베이크. (덩치 큰 적이 벽에 끼는 문제 회피.)

> 미구현/후순위: LOD 컨트롤러, 크기별 navmesh 베이크, 접근 경로 vs 근접 포위 블렌딩, 포메이션 슬롯
> 풀링(매 프레임 배열 할당 제거). 현재 1차 구현은 **포위 슬롯 + AgentMover(벽 통과 차단)** 까지.
>
> **부수효과(결정됨):** 멤버 회피(RVO)가 플레이어를 떠밀던 문제 → **플레이어는 안 밀림**으로 결정.
> NavMeshAgent.avoidancePriority 로 처리(플레이어 50=더 중요 / 몬스터 60=덜 중요). 몬스터는 플레이어를
> 피하되 밀지 못함.

## 12. 적 이동 AI — 시야 회피 기반 유틸리티 스코어링 (요청 반영)

> 11.3의 "고정 슬롯 포위(`EncircleFormation`/`encircleRadius`)"를 대체하는 상위 모델.
> **포위는 목표가 아니라 결과다.** 몬스터는 포위하려고 움직이는 게 아니라, 플레이어의 **시야를 피하려는
> 성질** 때문에 이리저리 움직이고, 그 결과 "어쩌다 보니 플레이어 주위에 있더라"가 되어야 한다.

### 12.1 핵심 원칙
- 포위는 **창발(emergent)**. 일정 간격으로 줄 세우지 않는다. (현재 구현은 너무 균일 → 교체 대상.)
- 모든 행동은 **즉각적이지 않다**. 시야에 들어왔다고 바로 피하면 "너무 정직하고 재미없음". 점수로
  판단해 **움직일 수도, 안 움직일 수도** 있다(관성/이력 + 확률).
- 간격(플레이어와의 거리, 몬스터끼리의 거리)은 **정확히 지킬 필요 없음** — 선호 점수일 뿐.
  자연스러운 포위, 혹은 자연스러운 **와해** 둘 다 허용.

### 12.2 플레이어 "시야"의 정의 (몬스터가 의식하는 것)
몬스터는 플레이어의 **시야각(view cone)** 을 의식한다. "바라본다"는 두 가지 의미:
1. **현재 플레이어 forward** — 지금 향한 방향의 콘.
2. **직전 공격 시점/방향** — 최근 공격이 향했던 방향(시간이 지나면 감쇠).

→ 둘이 합쳐져 "지금 노려봐지고 있다"는 **압박(pressure)** 점수를 만든다. (합성 가중치/감쇠율은 TBD.)

### 12.3 회피 행동 (가능할 때만, 선호 순서)
몬스터 능력(설정)에 따라 쓸 수 있는 수단이 다르다:
1. 플레이어 시야 콘에서 빠지려 한다(콘 밖 위치 선호).
2. **좌우걸음(strafe)** 가능하면 → 옆으로 피함. (= 이동에 그 방향을 바라볼 필요 없음 = 바라보는 방향과
   이동 방향이 분리된 몬스터.)
3. **뒷걸음(backstep)** 가능하면 → 뒤로 빠짐.
4. 체력이 낮으면 **그냥 도망** — 단, "도망친다" 지능 플래그가 있는 몬스터만.

### 12.4 유틸리티 스코어링 (간격 강제 없는 자연스러운 포위)
멤버는 고정 슬롯이 아니라 **후보 목적지(dest)에 점수를 매겨** "나는 저기쯤이 좋겠다"를 고른다.
점수 항(가중합, 몬스터별 튜닝):
- 플레이어 시야 콘 회피(압박 클수록 콘 밖 선호) ← 핵심 동인.
- 플레이어와의 선호 교전 거리(근접/원거리별로 다름).
- 다른 몬스터와의 소프트 간격(겹침 회피, 강제 아님).
- 행동 비용/패널티(좌우걸음 < 회전후전진, 뒷걸음 비용 등 — 몬스터별).
- 관성/이력(현재 위치 유지 보너스 → 즉각 반응 억제, 잦은 떨림 방지).

### 12.5 거리 레짐
- **멀면**: 군집 행동 없이 그냥 **본인 최고 속력으로 직진**(포위/스코어링 비활성).
- **근접 교전권**: 위 스코어링으로 시야 피하며 어슬렁 → 자연 포위/와해.
- **원거리 몹(추후)**: 선호 사거리 이상으로 좁히지 않음 — 조금씩만 움직임.

### 12.6 설정화 (후순위)
위 모든 항(시야 민감도, 회피 수단 가능 여부, 행동별 패널티, 도망 지능, 선호 거리, 반응 둔감도 등)은
**몬스터별 설정(config)** 으로 잡혀야 한다. 단 **설정 스키마 설계는 후순위** — "몬스터 설정을 얼마나 잘
짤지"를 먼저 검토한 뒤 확정한다(2장 `MonsterDef` 와 연결).

> 구현 메모: 현재 `EncircleFormation`(고정 슬롯) + `MonsterPack.encircleRadius` 는 **임시 플레이스홀더**.
> 위 스코어링 모델로 대체 예정. `IMemberMover`(AgentMover)·navmesh 구속·회피 우선순위는 그대로 활용.
>
> 열린 질문(추후 결정): (a) 현재 forward 와 직전 공격 방향의 합성 가중치·감쇠, (b) 후보 목적지 생성
> 방식(몬스터 주변 샘플 / 플레이어 링 / 그리드), (c) 몬스터 설정 스키마 — 위 12.6.

## 13. 몬스터 설정 스키마 (확정 — 린)

§12.6의 "설정화"를 합성형 ScriptableObject 2종으로 구현. 범위는 **린**(전투/활력은 최소 stub,
후속 `CombatProfile` 로 분리). 행동 성격은 **별도 재사용 SO**.

- **`MonsterDef`** (SO) — "무엇인가": 정체성(id/태그), 몸체(bodyPrimitive/sizeClass/scale/color),
  이동 능력(moveSpeed/turnSpeed/`canStrafe`/`canBackstep`), 활력(maxHP)/preferredRange, 특수능력
  (`abilities`: Leap/Burrow/Summon), 지능(canFlee/fleeHpRatio), 그리고 **3 프로필 참조**: `movement`
  →MovementProfile, `defense`→DefenseProfile, `attack`→AttackProfile.
- **`MovementProfile`** (SO) — "어떻게 움직이는가"(재사용): 시야 인지(콘 각/사거리/공격 기억),
  반응 둔감(reactionThreshold/repositionInterval/actChance), 스코어 가중치(wViewAvoid/wPreferredDist/
  wNeighborSpacing/wInertia), 행동 비용(costTurnThenMove/costStrafe/costBackstep).

시작용 콘텐츠: `Tools/Spawn System/Create Sample Monster Defs` → `Assets/GameData/Monsters/` 에
프로필 2종(MP_Aggressive/MP_Skittish) + 몬스터 4종(스웜링/러너/표준/브루트, §11.1) 생성.
`MonsterPackSpawner.monsterDef` 에 꽂으면 크기/색/속도가 def 에서 적용됨.

> SO로 분리 완료(이동/방어/공격 3 프로필) + `DamageResolver`(장갑/약점 규칙) + 로스터 8종 author링.
